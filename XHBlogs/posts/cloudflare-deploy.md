![搬家现场](/images/cover-cloudflare.jpg)

起因特别朴素：现在的小站挂在 Vercel 上，域名是 `xxx.vercel.app`，在国内属于"薛定谔的链接"——刷新十次能开三次，面试官要是正好赶上打不开的那三次，简历上写一句"个人博客"就成了负分项。朋友甩给我一个 `digitalplat.org`，说能免费注册域名、还能配 Cloudflare 加速。我兴冲冲点开，结果发现这玩意的真正卖点是**免费域名**，加速和部署还得靠别家。真正要解决的，从来是"把部署挪到国内不那么卡的地方"。

于是有了这一下午。

## 第一道坑：代码根本没在仓库根目录

迁移第一步是连 GitHub。 Cloudflare 让我从列表里挑仓库，我一眼锁定 `XinghuisamaBlogs`。但真去连的时候，构建死活找不到 `package.json`。

查了下本地才反应过来：我的博客代码不在仓库根目录，而是塞在子文件夹 `XHBlogs/` 里，根目录还躺着写作控制台、脚本、日志一堆东西。在 Cloudflare 里得把"根目录"手动填成 `XHBlogs`，它才找得到入口。

更吓人的是第二件事——我本地领先 GitHub **17 个提交**，GitHub 上那份是两个月前的老空壳。要是当时手快直接连上构建，部署出来的就是个啥都没有的站。得先把这 17 个提交推上去。

而"推上去"这三个字，在今天差点要了我的命。

## git push：和国内网络的持久战

第一次 `git push`，五分钟没动静，工具超时把它杀了。我一度以为失败了，后来才搞明白：仓库历史里带着照片墙的大图，打包要传的数据量摆在那，国内直连 GitHub 又是出了名的抽风。

改成后台跑，结果时好时坏——`api.github.com` 时不时能通，`github.com:443` 却动不动 21 秒超时、连接重置。折腾半天才发现我电脑上一直开着代理（自由猫，系统代理 `127.0.0.1:7892`），**但 git 这个铁头娃不读系统代理**，非得显式告诉它。加一句 `-c http.proxy=...`，秒推成功。这一条我后来专门记进了踩坑笔记。

教训：下次推送卡住，先别怀疑人生，先怀疑网络，再怀疑自己。

## 名字，又是名字

配置终于跑通、构建变绿，却在最后一步"部署"红了两次，两次都是同一类问题——**名字对不上**。

第一次：我本地的 `wrangler.jsonc` 里 Worker 名字叫 `my-blog`，Cloudflare 后台却按项目名要求叫 `xinghuisanblogs`。改名字，重推，重试。

第二次还是那个名字相关的报错，但这次是个"鸡生蛋"死锁：配置里有个"自引用"绑定，指向一个还没被创建出来的 Worker。查了下是首次部署的经典陷阱，直接把那块没用的自引用配置删掉，绕过去了。

## 真正的 BOSS：文章页全在偷偷报错

界面终于全绿，域名也绑好了，我美滋滋点开文章——**500**。所有归档文章、杂谈详情页，全挂。可首页、说说、照片墙又是好的。当时心里一凉：是不是内容搬家搬丢了？

赶紧去仓库点货：`posts/` 六篇文章、`moments/` 近百篇说说（含那本诗集）、`chatters/` 杂谈，一篇没少，全都在。根本不是丢数据，是**渲染方式在 Cloudflare 上水土不服**。

原理其实不复杂：全站的文章都是从 `.md` 文件里现读的，读文件用的是 Node 的 `fs` 模块。首页、说说这些在构建时就被烘成了静态 HTML，压根不在运行时读文件，所以没事；而 `/文章/某篇` 这种详情页是请求时才去现场渲染，一运行时调 `fs`——Cloudflare 的运行环境 `workerd` 里**根本没有 `fs` 这个东西**，当场 500。同一段代码在 Vercel 那种 Node 环境里跑得欢，一换平台就露馅。

## Turbopack 一口吃掉了我的补丁

找到病根，我想着把 markdown 在打包时就内联进去，别再运行时读文件了。写好了配置，一构建直接给我报错：

> This build is using Turbopack, with a `webpack` config and no `turbopack` config.

——Next 16 默认改用 Turbopack 打包了，我那套针对 webpack 写的补丁，它看都不看，直接无视。等于我对着一个不存在的引擎调了半天参数。

## 最后一块拼图

真正优雅的解法其实官方就备好了，还不用我动那八个读文件的文件、不碰写作控制台：让 Cloudflare 的**静态资源本身**充当缓存，把预渲染好的文章在构建时就烘进要上传的资源里，运行时直接读缓存，再也不用碰 `fs`。

只多加了一步 `populateCache`——把构建产出的预渲染缓存拷进要上传的资源目录。少这一步，照样 500。

我在本地起了个真·Cloudflare 运行环境试了下：那篇一直 500 的文章，返回 200，正文六万多字符，一个字没少。

## 今天的战果

- 小站从 Vercel 迁到了 Cloudflare Workers，4 个后端接口（AI 猫、天气、网易云、GitHub）全保留；
- 顺手把天气接口换成了免密钥的方案，白捡一个不用再申请 API Key 的功能；
- 域名从 `vercel.app` 换成了朋友推荐的免费域名 `ephemeralbloom.dpdns.org`；
- 顺便把 Next 从 16.2 升到 16.3.5，Vercel 那边先留着当备胎。

回头看，这趟最值钱的不是那个新域名，而是我算是把"一个 Next.js 全栈站到底怎么在云端跑起来"这件事，从黑盒变成了几个能自己解释的齿轮：构建、打包成 Worker、上传资源、读缓存。以前这些词对我就是一团雾，现在雾里大概能摸到几个开关了。

至于值不值——等哪天有人问我简历上那句"独立部署"具体干了啥，我不用再心虚地含糊过去，这就够了。
