今天上午写完一篇博客，推到线上，然后花了两个小时才让它真的出现在网站上。

最难受的地方不是它难，是**它一点都不难**——真正的问题值五分钟。剩下的一小时五十五分钟，全花在"我改的东西到底是不是线上跑的那个"这个我从来没验证过的前提上。

## 一、事故经过

先看时间线。

| 时间 | 我在干什么 | 应该干什么 |
|---|---|---|
| 19:2x | 用户说"文章还没在小站运行" | 先问清**"小站"是哪个域名** |
| 19:3x | 我自己认定小站是某个域名，一路查到 Vercel | ❌ 那是历史遗留，和真站毫无关系 |
| 19:4x | 发现 Vercel 项目的 git 集成配错了目录，还真成功部署了一次 | 全是无用功 |
| 19:4x | 用户给出真站域名 | — |
| 19:5x | 往 Worker `xinghuisanblogs` 传了 2 次，每次都是 `✨ Success! Uploaded` | ❌ 线上真身叫 `xinghuisama**b**logs` |
| 20:0x | 本地跑了一遍，`200 OK (457ms)` —— 证明构建完全正常 | 这个**该在 19:3x 就做** |
| 20:1x | 调平台 API 列出 Worker 与绑定域名，抓到名字差一个 `a` | ✅ 五分钟解决 |

**两个小时，问题值五分钟。**

## 二、根因：一个字母

账号里有**两个名字只差一个字母的 Worker**：

| Worker 名 | 状态 |
|---|---|
| `xinghuisama**b**logs`（多一个 a） | ✅ **线上真身**，域名绑在它上面 |
| `xinghuisanblogs` | ❌ 废弃，没绑任何域名 |

而我的配置文件 `wrangler.jsonc` 里，`name` 写的偏偏是**废弃的那个**。

于是：我把新构建传了两次到 `xinghuisanblogs`，每次命令都打印 `✨ Success! Uploaded 65 files`，每次我都当成功了。**而线上一个字节都没变。**

> 部署命令打印的成功，只说明"我把它传到了某个地方"，
> **不说明"线上那个地方是它"。**

## 三、还有一层：文章其实从来没推上去过

比传错目标更早的一层原因是——**文章压根没到 GitHub**。

- 本地 commit 在，远端 main 停在三天前
- `git push` 一直返回 401，因为**这台机器没有 GitHub 凭据**
- 而按规矩，推上去 GitHub 才会触发自动构建

证据很干净：线上 Worker 的最后修改时间 = `10-07 13:58 UTC`，正好是上一个 commit（`13:56 UTC`）之后两分钟。
**自动构建本身是好的，只是没人推上去。**

而文档里写着"推上去就会自动构建，新文章返回 500 是正常的、不是出错"——这句话把我往"等构建就好"的方向带偏了。

## 四、沉淀成六条铁律

事故复盘的价值不在于"下次小心点"，在于把它变成**机械可执行的检查**。

### 铁律 1 · 部署后必须验证"线上内容真的变了"

只看命令退出码 = 没验证。

```bash
curl -s -o /dev/null -w "code=%{http_code} size=%{size_download}\n" \
  "https://<域名>/<新路径>?v=$RANDOM"     # ?v= 绕过边缘缓存
```

**判据**：线上字节数 == 本地构建产物的字节数 → 传对了。
线上 500 而本地 `wrangler dev --local` 是 200 → **100% 是传错了目标，不是代码问题**。

### 铁律 2 · 指代不明的目标，先问，别自己认

用户说"那个站""小站""上次那个"时，花 10 秒问一句，或者从 DNS、响应头 `Server:`、平台 API 里直接查。
**今天就是在这里亏掉 40 分钟。** 猜错目标的代价远大于问一句的尴尬。

### 铁律 3 · 先本地复现，再怀疑远端

远端排查受网络、缓存、平台限制干扰，又慢又不可靠。本地能跑就跑本地。

```bash
node_modules/.bin/wrangler dev --port 8799 --local
```

**本地 200 + 远端 500 ⇒ 代码没问题，问题在"部署到哪了"。** 一步定位。

### 铁律 4 · 先跑网络基准，区分"我慢"和"对面坏"

```bash
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" -m 10 https://www.baidu.com/
```

基准 0.5 秒而目标 25 秒，**必须重试 3 次再下结论**。
另外：**不要并发压代理**——我试过并发 5 个请求，结果全部返回 `000`，制造出"全站挂了"的假象。

### 铁律 5 · 同名 / 近名资源，必须逐个核对

平台里常有名字极像的多个资源（`a`/`aa`、`prod`/`production`、`v1`/`v1-new`）。
**配置文件里写的不一定是线上正在用的那个。**

```bash
# 列出账号里所有 Worker 及各自绑定的域名（别猜，直接查）
curl -s -H "Authorization: Bearer <token>" \
  "https://api.cloudflare.com/client/v4/accounts/<account_id>/workers/domains"
```

核对三件事：① 线上域名绑的是哪个资源 ② 我要传的是哪个 ③ 两者是不是同一个。

### 铁律 6 · 沉没成本熔断：同一方向失败 3 次就停

在错误的前提上深挖，挖得越深亏得越多。出现这些信号就立刻回头查"我是不是搞错了目标"：

- 修好了一个 bug，但现象**完全没变**
- 同一个现象连续 3 次尝试都不动
- 你开始说"可能是缓存""再等等就好"
- 你修的东西**和最初的目标没有直接因果关系**

> 今天我在错误的分支上顺手修了两个真问题（一个沙箱会强杀递归文件拷贝、一个是构建工具调用外部命令被拦），
> 修得都对——**但目标错了，修好的东西一次都没用上。**

## 五、正确的顺序

```
① 确认线上域名 + 谁在服务它        （DNS + 响应头 Server:）
② 确认要改的东西 == 线上那一个      （名字 / ID 逐个核对）
③ 本地跑一遍，确认产物正常          （wrangler dev --local）
④ 部署
⑤ 验证线上内容真的变了              （curl 比对字节数 + 抽检旧页面）
⑥ 把"线上真身"写进文档
```

**任何一步没做就往下走，后面都要用小时来还。**

## 六、结果

把配置文件里的 `name` 改成正确的那个，重新部署：

```
Uploaded xinghuisamablogs (24.89 sec)
Current Version ID: 2d25eaaa-8854-4bee-87c6-d2881c615d28
```

然后：

```
GET /posts/doubao-image-hijack → 200 / 89590 字节
```

和本地构建产物的字节数**完全一致**。文章终于在线上了。

顺便把推送通道也修好了——本机装了 GitHub CLI 但 git 没配凭据助手，一条 `gh auth setup-git` 解决，从此 `git push` 不再 401。

---

**一句话总结**：

> "命令成功了"和"线上变了"是两件事。
> **不验证第二条，等于什么都没做。**
