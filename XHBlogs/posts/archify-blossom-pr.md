前几天我翻自己的 B 站收藏夹找乐子，翻到一个讲 Archify 的视频。当时只记得「哦，能画图」，就收藏了。今天回头打开它，发现是 66k 星的仓库，MIT 协议，而且已经有 130 多个待处理 issue——说明它活着，而且有人管。

## 这东西是干嘛的

一句话：**它让 AI 助手画出来的图，不再是 ASCII 字符画。**

你在 Cursor / Claude Code / Codex / OpenCode 里描述一个系统，agent 输出一份结构化 JSON，Archify 把它确定性地编译成一张**单文件、离线可用、可交互**的 HTML 图。五种图类型（架构 / 流程 / 时序 / 数据流 / 生命周期），深浅主题，能搜节点、能导出 PNG/SVG。

它的卖点我觉得是这句：**每一条线都有出处，不瞎编拓扑。** 这话不是营销——我后面被它的布局验证器挡了两次，才知道是真的有硬约束。

## 我想加的东西

它原本有 4 套视觉预设，每套对应一种场合：

- **classic** — 稳定默认
- **signal-flow** — 动态演示
- **blueprint** — 工程评审
- **editorial** — 发布说明

看出来了吗？四套全是**工程场合**。没有一套是「个人作品展示」用的。你把架构图放到个人站或者作品集里，用 blueprint 那套，看起来就像内部工具漏出来了。

所以我加的第五套叫 `blossom`：语义配色和几何**完全不动**，只换表现层——暖玫瑰底、1.75rem 大圆角、柔和光晕、圆形角标。

（对，和我这个博客一个色系。毕竟是给自己用的。）

## 配色是整件事里最简单的部分

写 CSS 变量大概花了两小时。剩下的时间全花在别的地方。

因为 Archify 的模板是**内联**进每个产物的。我改了 `viewer/template.source.html` 一行，所有渲染出来的 HTML 全都变了。所以要重建的东西是：

- 两套示例（开发用 + 打包用），各 5 个文件
- gallery 页面 + manifest + 11 个 gallery 产物
- README 里那个动图
- 一个叫 `checkout-platform-delta` 的对比页
- 还有一个 `archify.zip`

而这些产物本身也是「源码 → 生成器 → 产物」的链路，中间还夹着校验（`--check`），产物过期会直接测试失败。

## 三个把我按在地上摩擦的坑

### 一、`archify.zip` 有两个硬门槛

第一，构建脚本硬校验 **Node 22**。我本机是 24，直接拒绝执行——因为 zip 的字节依赖 Node/zlib 的工具链，换个版本构建出来的字节就不一样，而 CI 会重新构建一遍然后逐字节比对。

第二，打包脚本要 `git ls-files` 拿文件的 index modes。我一开始把克隆下来的子 `.git` 删了（怕污染主仓库），结果它直接报 `required package input is not tracked by Git`。

解决办法是重新克隆一份带 `.git` 的，把改动同步进去，用便携版 Node 22 构建。构建完我又重跑到另一个路径 `cmp` 了一次，确认字节稳定，才敢推。

### 二、一个被掩盖的错误

重建 README 动图时，脚本只报了一行 `EPERM ... rmSync`——删临时目录失败。

但真实错误根本不是这个。那个脚本把删除放在 `finally` 里，`finally` 抛出的异常会把 try 块里的真实错误**顶掉**。我写了个 wrapper 把 `fs.rmSync` 包一层吞掉异常，才看到真相：

脚本用 `sh -c 'command -v ffmpeg'` 找 ffmpeg，Windows 下返回的是 MSYS 风格路径 `/c/Users/...`，Node 根本执行不了，所以 `ffmpeg failed` 而且 stderr 是空的。

这种「错误信息指向 A，真凶是 B」的情况，我觉得比错误本身更值得记一笔。

### 三、`finally` 之外，还有个路径分隔符

动图重录之后，记录文件里的路径被写成了 `docs\assets\...`（Windows 反斜杠），而仓库约定是正斜杠。测试直接报字符串不等。手动改回来。

## 怎么证明「我没弄坏东西」

这是我觉得整件事里最值钱的一课。

我一开始的想法是「跑一遍测试，没报错就行」。但 Windows 上跑出来 17 个失败。这时候你怎么知道这 17 个是你弄坏的，还是本来就这样？

**做基线对照。**

我把改动 `git stash` 收起来，在同一个克隆里跑一遍全量测试；再恢复改动，跑第二遍。然后逐条比对失败列表。

结果是：**两边一字不差。** 1262 个测试、1238 通过、17 失败、7 跳过，连 17 个失败的名字都完全一致。这 17 个全是 Windows 环境固有的（git 的 `\\.\nul` 路径 bug、`SIGTERM` 行为差异、ESM loader 不认裸 Windows 路径之类）。

有了这个对照，「零回归」才是个**结论**，而不是一句感觉。

## CI 结果

10 项检查全绿，包括四个 Node 版本（18/20/22/24）的测试、三个系统的打包冒烟测试，以及那个最关键的 `zip-freshness`——它在 Ubuntu + Node 22 上重新构建 zip 然后逐字节比对。我在本地先自己对过一遍，所以推上去的时候不太慌。

PR：https://github.com/tt-a1i/archify/pull/473

## 收获

配色是最好写的。难的是**一条链路上所有下游产物都得跟着重建**，以及**证明自己没弄坏东西**。

说实话中间有一段时间我是懵的——产物太多，改一个动全身，我一度搞不清楚哪些是「源码」哪些是「生成物」。后来把链路画出来才理顺：模板是源码，产物是结果，中间夹着生成器，改源码就必须重跑生成器。

下次再给别的项目提 PR，这套流程我可以直接复用。
